# GUI architecture

## Status and scope

The shared GUI path now has three separate layers:

- immutable read-only state in `pc_controller/gui_model.py`;
- one Fake-only controller owner in `pc_controller/gui_runtime.py`;
- a PySide timer binding and renderer in the copied 4WIS dashboard.

This remains read-only with respect to ControllerApp and hardware output. The
Calibration tab can now hold Servo Zero, Servo Angle endpoint, and
Direction/Coordinate candidates in widget-local drafts, but
it does not enable real Serial, ARM, drive, calibration output, config writes,
fault injection, or Competition control from the GUI.

The copied dashboard under `apps/robot_pc_system_4wis_dashboard/` keeps its
existing navigation and visual intent. Its original text-command, Mock, and
simulation paths are not treated as the authority for current v29 robot state.

The shared window now uses the command-center shell defined in
`widgets/command_center_style.py`: an original cut-corner status fascia, a
left operation rail, centralized dark/green/orange/yellow/red tokens, and the
same keyboard-focus semantics as the existing Qt widgets. Existing renderer
widgets remain the functional screen bodies; the shell does not replace them
with an image. The full legacy dashboard also consumes the same visual tokens
without removing its original tab navigation.

Original transition sounds are isolated in `sound_manager.py`. The manager
diffs immutable fleet snapshots, applies per-event cooldowns, suppresses
offscreen/test playback, and fails soft when QtMultimedia or an audio device is
unavailable. Sound settings are stored independently from vehicle/controller
configuration.
The shared runtime now includes Main Dashboard, Drive Diagnostic, Mechanism
Diagnostic, Sensor Diagnostic, Calibration/Servo Zero/Angle/Direction,
Fault / Warning History, Autonomy, local Competition Logs, and offline Replay foundation tabs.
The first seven consume the same immutable fleet snapshot rather than a legacy
data source; Logs consumes only an explicitly selected, validated local JSONL
and uses the fleet snapshot solely to synchronize R1/R2 view selection. Replay
consumes the same immutable Logs source plus a GUI-local R1/R2-isolated cursor.

The intended navigation remains:

```text
Dashboard
├─ R1
│  ├─ Drive
│  ├─ Mechanisms
│  ├─ Sensors
│  ├─ Calibration
│  ├─ Faults / Warnings
│  ├─ Autonomy
│  ├─ Logs
│  └─ Replay
├─ R2
│  ├─ Drive
│  ├─ Mechanisms
│  ├─ Sensors
│  ├─ Calibration
│  ├─ Faults / Warnings
│  ├─ Autonomy
│  ├─ Logs
│  └─ Replay
├─ Field
├─ Competition
└─ Settings
```

The copied 4WIS dashboard includes a read-only `Main Dashboard` tab. It
renders `FleetDashboardSnapshot` data injected through
`MainWindow.set_fleet_dashboard_snapshot()` and retains the existing Home and
diagnostic navigation in the legacy launch mode. The renderer does not open
Serial, build Fake-only state, or expose ARM/drive/calibration actions.

The explicit shared runtime entrypoint constructs
`MainWindow(shared_runtime_only=True)`. That safe mode creates only the Main
Dashboard and output-free Drive, Mechanism, Sensor, Calibration, Fault /
Warning History, Autonomy, Logs, and Replay tabs: it does not
construct the legacy `ConnectionManager`, `ESP32Serial`, camera, COM-port
enumeration, legacy update timer, or legacy command tabs. This limited
navigation is intentional while shared screens are added incrementally; the
existing full dashboard mode remains unchanged.

Field and Competition screens remain separate milestones. Servo Zero,
Servo Angle endpoint, and Direction/Coordinate local draft editing are present;
physical validation, output, and persistence remain later controller/API milestones.

## State and backend flow

```text
Controller / Autonomy
        |
   SafetyMonitor
        |
 ControllerApp (one owner)
        |
 VirtualSerial -> SimulatedEsp32
        |
 read-only RobotDashboardSnapshot
        |
 FakeFleetDashboardRuntime
        |
QtFleetDashboardBinding -> GUI renderer
```

The persistent log branch is separate:

```text
explicit local Competition JSONL
        |
 strict read-only validation
        |
 bounded CompetitionLogSourceSnapshot
        |
 R1/R2 + FLEET filter -> Logs renderer
        |
 inert retained records -> local Replay cursor -> Replay renderer
```

This branch never scans directories, merges the session-local Fault History,
controls Competition, emits recorded commands, stages an outbox, or transfers
data remotely.

`ControllerApp` now retains the last requested body motion and the last v29
drive message generated by its normal safety/control path. The GUI model reads
those values together with `SafetyMonitor`, accepted telemetry, node identity,
reconnect phase, and optional autonomy/competition context. It never writes to
Serial and exposes no ARM or drive method.

Backend identity is always explicit:

- `REAL_SERIAL`: physical-serial code path; hardware success is not implied.
- `FAKE_ESP32`: `VirtualSerialLink` plus `SimulatedEsp32`, using real NDJSON.
- `LEGACY_SIMULATION`: direct simulator path, visibly distinct from Fake ESP32.
- `UNBOUND`: no controller is assigned to that robot.

## R1 and R2 binding

A caller must explicitly bind a `ControllerApp` snapshot to `RobotId.R1` or
`RobotId.R2`. `build_fleet_dashboard_snapshot()` fills an unbound robot with an
OFFLINE/UNKNOWN placeholder and never copies the other robot's vehicle, node,
telemetry, or autonomy state.

The Fake GUI entrypoint therefore requires `--robot R1` or `--robot R2`; it has
no default robot mapping. Changing the selected robot in the GUI changes only
the view. It does not rebind the controller or copy the bound robot into the
unbound slot.

The repository currently has one confirmed default node identity,
`mcb44_drive_main`. There is no authoritative config mapping that identity to
both R1 and R2, so the GUI model does not invent one.

## Dashboard state

Each immutable robot snapshot includes:

- ONLINE, OFFLINE, RECONNECTING, or BLOCKED communication state;
- Safety state, SAFE, READY, ARM_PENDING, ARMED, fault, and warning state;
- controller connection, reconnect phase, message ages, and telemetry sequence;
- required/optional node status, including missing, duplicate, and wrong-role;
- requested `vx`, `vy`, resultant magnitude/direction, and `omega` direction;
- exact v29 wheel command fields plus observed RPM, PWM, steering, and encoder;
- available battery fields without generating dummy battery data;
- autonomy mission/state/current step/retry/fallback context;
- Competition state when an existing `CompetitionSession` supplies it;
- structured fault source, node, reason, timestamp, flags, and Safety response.

The Main Dashboard renders both R1/R2 overview cards and a selectable detail
view with prominent Safety/fault state, controller/communication status,
autonomy/Competition context, available battery telemetry, node inventory, four
wheel command/observed values, and simultaneous translation/rotation graphics.
Changing R1/R2 selection only changes the local view and emits a selection
signal; it does not mutate a controller or send a command.

The Drive Diagnostic tab derives a toolkit-independent
`DriveDiagnosticSnapshot` from the selected `RobotDashboardSnapshot`. It shows
command direction/target, observed RPM/PWM, commanded and observed steering,
motor/servo inversion, wheel status, drive-node link status, and simultaneous
translation/rotation graphics. A second robot-layout canvas places all four
wheels around the chassis with distinct command and observed arrows.

Steering fields are rendered only when the configured `drive_type` is `4WIS`;
an OMNI/unknown robot is not given fabricated steering state. The current node
manifest identifies a drive-role node but has no per-wheel node mapping, so the
screen labels its node link as role-level instead of inventing four links.

The Mechanism Diagnostic tab derives a toolkit-independent
`MechanismDiagnosticSnapshot` from the same selected robot snapshot. The
current authoritative config, telemetry, and default node manifest define only
the drive motors, wheel encoders, steering servos, and `mcb44_drive_main` drive
node. Candidate 270-degree servos, legacy actuator buttons, and disabled
hardware-profile notes are not current non-drive mechanism state.

Consequently, the current bound robot renders `NOT_CONFIGURED` with no
mechanism rows. Drive-role nodes are explicitly delegated to Drive Diagnostic
and sensor-role nodes to the future Sensor Diagnostic. If another non-drive
node appears, it is displayed only as `UNMAPPED`; command, state, limit,
telemetry, and fault cells stay `N/A` until an authoritative per-robot
mechanism inventory and telemetry contract maps them. A node identity alone is
never promoted to a mechanism.

Invalid or non-finite optional telemetry is displayed as unknown. It is not
coerced into plausible robot data.

The Sensor Diagnostic tab derives a toolkit-independent
`SensorDiagnosticSnapshot` from the same selected robot snapshot. The current
default manifest contains only the drive-role `mcb44_drive_main`, and the
current v29 firmware telemetry contains wheel encoder/RPM, motor PWM, steering,
fault flags, and command age. Wheel encoders remain owned by Drive Diagnostic;
there is no authoritative per-robot non-drive sensor inventory, unit/validity/
stale policy, or generic sensor telemetry mapping in shared state.

Consequently, the current bound robot renders `NOT_CONFIGURED` with no confirmed
sensor rows. A sensor-role node is displayed only as `UNMAPPED`; its identity is
not promoted to a named sensor and no value, unit, validity, stale state, fault,
or last-update time is invented. The legacy dashboard's MockSensors, DUMMY
status lines, disabled IMU/LiDAR hardware profile, and prototype LSB CSV stream
are explicitly excluded from live shared state. A global Safety fault remains
prominent but is not assigned to an unconfigured sensor.

## Safety boundary

GUI renderers must remain read-only consumers of snapshots. Future buttons must
call a controller-level API which enforces `SafetyMonitor`; a renderer must not
write v29 messages or legacy drive text directly.

The Fake runtime exposes no ARM, drive, calibration, or fault-injection method.
Startup uses the existing fail-closed reconnect handshake gates in the order
`DISARM -> HELLO/identity -> CONFIG -> config_ack`. Periodic ticks provide zero
operator input. Window close stops the Qt timer, sends a final DISARM over the
sole VirtualSerial link, and closes that link.

Reconnect remains fail closed. RECONNECTING and BLOCKED are not READY, and a
recovered transport remains READY_DISARMED until a later explicit ARM. Duplicate
node identities are shown as an error and are never collapsed into one selected
device.

The first Safety reason remains latched for the diagnostic epoch. If an explicit
ESP32 fault arrives after a SAFE telemetry response, the snapshot preserves both
the Safety response reason and the later structured ESP32 fault event rather
than overwriting either one.

## Fake mode

Fake GUI validation must construct the same `ControllerApp` used by normal
control with `--fake-esp32`. Its state travels through `VirtualSerialLink`, the
NDJSON codec, `SimulatedEsp32`, `SafetyMonitor`, and then the snapshot model.
GUI-only fake business state is prohibited.

The explicit launcher is:

```powershell
.\run-fake-robot-dashboard.cmd --robot R2
```

Use `R1` instead only when that is the intended explicit binding. The other
robot remains UNBOUND/OFFLINE. Existing `run-robot-dashboard.cmd` and
`run-robot-dashboard-4wis.cmd` launchers are unchanged and are not the shared
single-owner runtime path.

Debug fault-injection controls are not implemented in this milestone. When
added, they must be available only for `FAKE_ESP32`, disabled for real serial,
and disabled in active Competition mode.

## Field coordinates

No field coordinate or object-pose model was added here. Future integration must
use repository-backed F3RC field data, retain physical units separately from
pixels, and label unknown dimensions as unknown. Existing optional dashboard
field code is not yet connected to this shared controller snapshot.

The corrected GUI-032A source audit found a local F3RC2026 Ver 1.1 rulebook in
the historical folder. It is excluded by `.git/info/exclude`, is not retained
in Git HEAD, and has not been checked against the latest official-site
revision. Its SHA-256 and page-level rule evidence are recorded in the audit.
The rulebook establishes the object/zone vocabulary, setup counts, and
qualitative access/placement rules, but explicitly delegates dimensions and
geometry to a separate `Field drawing / objects` artifact that is still
missing.

The two copied dashboard YAML files and their Field-model implementations are
byte-identical, but that establishes copy consistency rather than authority.
Their numerical dimensions/zones/start poses remain unverified derived
candidates, their objects are explicitly provisional, and their
top-left/down-positive coordinate frame is a legacy renderer convention rather
than an approved mission frame.

`docs/f3rc_field_source_audit.md` records the rulebook and candidate hashes,
page references, partial authority boundary, and evidence required to unblock
Field modeling. Until the approved companion drawing/object package is
retained and every numerical candidate is reconciled, shared mission
dimensions, object poses, rotation/orientation, `face_down`, and coordinate
transforms remain `UNKNOWN`. No shared Field renderer or editor may promote the
legacy candidate values.

## Configuration editing and calibration

The Calibration foundation derives a toolkit-independent audit from
the selected `RobotDashboardSnapshot`. It shows the controller-loaded servo
logical name/channel, `center_us`, trim, calibrated flag, last commanded angle,
and observed angle when available. Current/saved configuration, absent pending
state, config-only validation, revert state, and apply state are separate fields.
`CONFIG_ONLY_VALID` is not physical calibration evidence and the displayed
saved value is not a live disk reread.

There is no controller-level Calibration API yet. `ServoZeroDraftStore` therefore
keeps candidates only in process memory and has no ControllerApp, Serial, file,
or output dependency. It validates integer `center_us` against the authoritative
configured min/max range and finite `trim_deg`, while preserving raw invalid input
for correction. Current and saved controller-loaded values never change when a
draft is staged. Drafts survive periodic snapshot refresh, remain isolated by
R1/R2 and servo, can be reverted locally, and are marked `STALE_BASE_CONFIG` if
the controller-loaded base changes underneath them.

The shared screen exposes only validate/stage and local revert actions. Apply and
save controls are present but disabled, and every row remains
`BLOCKED_NO_CONTROLLER_API`. There is no DEBUG/ARM action, Serial owner, config
write, or hardware output path. Future output must retain distinct validate,
apply, cancel/revert, and explicit save stages.

`ServoAngleDraftStore` follows the same output-free boundary for the current
authoritative endpoint representation: `min_us`/`max_us` paired with
`min_angle_deg`/`max_angle_deg`. Validation mirrors the existing PC/firmware
structural contract: the controller-loaded `center_us` must stay strictly
inside the pulse endpoints and the angle interval must cross zero. This is not
evidence that the mechanism can safely reach either endpoint.

Angle drafts are isolated by R1/R2 and logical servo, preserve invalid raw text,
and become `STALE_BASE_CONFIG` if the controller-loaded endpoints, center, trim,
or direction changes. Servo Angle drafts do not edit direction or calibrated
status; those remain distinct from angle endpoints, and the GUI cannot declare
a servo physically calibrated. Apply/save stay disabled and physical endpoint
validation is explicitly `REQUIRED_BEFORE_APPLY`.

`DirectionDraftStore` keeps controller input correction, the fixed machine
coordinate convention, logical front, motor polarity, and servo direction as
separate semantic layers. The shared immutable snapshot exposes the loaded
`axis_vx`/`axis_vy`/`axis_omega`, per-axis inversion, deadzone/scales, and the
existing kinematics convention `+X=forward`, `+Y=left`, `+omega=CCW`. It also
keeps the existing pure-pivot `pivot_direction_inverted` setting separate; that
setting is not treated as controller inversion, logical front, or wheel polarity.
The PC-only `mixed_omega_inverted` setting independently corrects yaw while a
translation command is active, without changing the verified pure-pivot direction.

The Direction editor can stage controller inversion, one of FRONT/RIGHT/REAR/LEFT
as a local logical-front candidate, and four independent motor/servo inversion
candidates. Current, pending, and controller-loaded saved values remain separate.
The current runtime has no persisted logical-front field, so the effective current
front is the existing fixed FRONT convention while saved logical front is visibly
`NOT_CONFIGURED`. Changing logical front does not rewrite motor wiring, servo
calibration, or sensor mapping.

The no-motion preview reuses the exact runtime controller-axis correction curve
and shows raw controller values, corrected normalized values, scaled machine-
relative values, the logical-front rotation, and the final local vx/vy/omega
preview. Logical-front rotation changes translation axes only; omega sign remains
the existing CCW-positive convention. Drafts are keyed by R1/R2, survive periodic
snapshot rebuilds, become `STALE_BASE_CONFIG` if their controller/machine/wheel
base changes, and can be reverted locally. Apply/save stay disabled, and the model
has no ControllerApp, Serial, config-file, ARM, DEBUG, or actuator output API.

Servo calibration must use SAFE -> explicit DEBUG calibration mode -> one
selected servo at bounded rate -> confirmation/save -> SAFE. Drive output must
remain zero for the whole calibration session. The renderer must not expose a
direct Serial debug path.

## Parameter editor foundation

`ParameterDraftStore` is a toolkit-independent, local-only parameter editor
foundation. It consumes only immutable `RobotDashboardSnapshot` values and has
no ControllerApp, Serial, config-file, ARM, DEBUG, or actuator-output API.

The first bounded set is deliberately limited to parameters whose PC runtime
clamp is authoritative in current source code:

- controller `deadzone`: `0.0..0.95`;
- controller `linear_scale` and `angular_scale`: `0.0..1.0`;
- PC motion `open_loop_max_pwm` and `pivot_max_pwm`: `0..1023`.

The PWM range includes the ControllerApp's existing zero sentinel semantics; it
does not mean zero output. After clamp and integer conversion, an open-loop value
of zero falls back to `1023`, while a pivot value of zero falls back to the
effective open-loop limit. The displayed effective current mirrors those rules
and keeps the raw controller-loaded value visible. Fractional PWM drafts fail
closed as `PENDING_REQUIRES_INTEGER`.

Each row keeps the controller-loaded value, effective runtime-clamped current
value, local pending value, valid range, source, validation, revert state, and
blocked apply state separate. Out-of-range controller-loaded values are shown
as `SOURCE_RUNTIME_CLAMPED` rather than silently hidden. Invalid, out-of-range,
and stale-base pending values fail closed locally. Staleness is scoped to the
selected source; pivot also tracks the open-loop source only when its current or
pending zero sentinel actually depends on that fallback.

The Calibration tab provides a slider plus numeric candidate editor. Moving a
slider changes only unstaged widget state; explicit stage writes only the
per-robot in-memory draft. Periodic snapshots preserve unstaged/staged values,
R1/R2 drafts remain isolated, and Apply/save are disabled. Speed, PID, servo
rate, and alignment parameters remain outside this first set until their
authoritative editable ranges and controller ownership contract are defined.

## Fault / Warning History foundation

`RobotDashboardSnapshot.diagnostic_events` keeps currently active diagnostic
semantics structured instead of forcing the renderer to parse warning strings.
PC Safety root causes, structured ESP32 fault messages, ESP32 telemetry flags,
timeout warning/stop states, transport errors, node inventory results, and an
unbound GUI binding notice retain separate sources. A PC Safety cause has no
node attribution unless the originating component provides one.

`FaultHistoryStore` observes event edges in immutable snapshots and retains a
bounded maximum of 200 entries per R1/R2 for the current GUI process. It does
not read ControllerApp, SafetyMonitor, Serial, or config directly. Repeated
periodic snapshots do not duplicate an active event; clearing the active event
marks the retained row `CLEARED`, and a later recurrence becomes a new row.

Exact structured ESP32 timestamps are labeled `SOURCE`. Events whose source
does not retain an event time use the first GUI observation timestamp and are
explicitly labeled `FIRST_OBSERVED`; that value is not represented as an exact
hardware event time. Severity, source, node/UNKNOWN, reason, timestamp basis,
fault flags, and Safety response remain separate fields.

Acknowledgement is per-event, per-robot session metadata only. Acknowledging
or unacknowledging a row does not clear the latched Safety root cause, change
READY, send Serial, ARM, write config, or delete history. There is intentionally
no clear/delete/apply control in this foundation.

The table preserves the selected event ID across periodic snapshot rendering.
This keeps local acknowledge/unacknowledge usable at the shared runtime's 100 ms
refresh cadence, including when newer rows change table positions. Selection is
cleared only when the selected retained event is no longer present.

## Autonomy screen boundary

The Autonomy tab derives a toolkit-independent `AutonomyScreenSnapshot` from
the immutable robot snapshot. When a caller explicitly supplies an existing
`AutonomyStateMachine`, the shared snapshot retains mission/state/current and
next step, attempt/retry budget and deadline, configured failure policy, active
fallback, skipped steps, terminal reason, and the most recent 20 state-machine
events. The renderer shows state ID and presentation name separately and labels
the next state as conditional whenever step outcome or external gates decide it.

`MissionStep` has a retry delay/deadline but no authoritative generic step
timeout. The screen therefore renders step timeout as
`NOT_CONFIGURED_IN_MISSION_STEP_CONTRACT` instead of inventing one. Similarly,
`HOLD_REQUESTED` and `STOP_REQUESTED` are state-machine action semantics; the
current machine does not retain executor acknowledgement, so the screen labels
executor confirmation `UNKNOWN_NOT_RETAINED_BY_STATE_MACHINE`.

The current single-owner Fake dashboard runtime intentionally owns no Autonomy
machine. Its bound robot therefore renders `NOT_CONFIGURED`, while the unbound
robot remains independently unconfigured. The tab has only local R1/R2 view
selection and constructs no ARM, START, STOP, SKIP, FALLBACK, executor, Serial,
config-write, or direct transition control.

`MissionStep.step_id` and `fallback_id` are policy identifiers, not an
authoritative physical task or pose target. The screen keeps Current Target at
`NOT_DEFINED_IN_MISSION_MODEL` instead of relabeling either identifier. Retained
HOLD/STOP context is explicitly last-request history, not current executor state.

## Logs screen boundary

`read_competition_log_records()` validates one explicitly supplied local
`.jsonl`/`.ndjson`. `CompetitionLogSourceSnapshot` retains at most the newest
1000 validated records, and the selected R1/R2 screen shows at most the newest
200 matching robot plus fleet events. No automatic log-directory discovery is
performed.

The model keeps session ID, sequence, timestamp, Competition event/state,
recorded state transition, robot/fleet scope, Autonomy, Safety/armed, fault,
retry, node, reason, and structured data fields separate. Fields that were not
persisted are rendered `UNKNOWN_NOT_RECORDED`; GUI Fault History events are not
promoted to persistent Competition truth. Invalid core or optional writer-owned
field types fail the whole source closed as `INVALID` with no partial rows.

The eighth tab starts `NOT_CONFIGURED`. A caller may bind exactly one path with
`--competition-log`; Reload re-reads only that path. R1/R2 selection remains
synchronized with the other tabs, while Logs owns no ControllerApp, Serial,
ARM, state-machine, Competition control, config-write, outbox, delete, or remote
API. POST_COMPETITION remains `AWAITING_REMOTE_CONFIGURATION` and
`remote_transfer_performed=false`.

## Replay screen boundary

`ReplayCursorStore` consumes only the bounded immutable
`CompetitionLogSourceSnapshot`. For each selected robot, its timeline contains
fleet records plus that robot's records and excludes the other robot. The cursor
is isolated by R1/R2 and remains stable when the same explicit log is reloaded.

The selected frame shows the exact recorded Competition event/state/transition.
Autonomy, Safety, and armed values carry forward only from fields explicitly
recorded on the selected robot's own events, with the source sequence shown as
`LAST_RECORDED_FOR_Rx@sequence=N`. Fleet records never become robot state. If a
bounded source dropped the prefix before any robot value was retained, the value
remains `UNKNOWN_RETAINED_PREFIX_TRUNCATED` rather than being backfilled.

The ninth tab provides only local First/Previous/Next/Last, slider, table-row,
and R1/R2 selection. Recorded actions and data remain inert text. Replay owns no
ControllerApp, Serial, ARM, Autonomy executor/state-machine call, Competition
control, config/outbox write, delete, automatic playback, or remote API.

fleet filtering, recorded state transitions, optional field UNKNOWN semantics,
and the remote-disabled boundary. `tests/test_logs_widget.py` covers the
read-only table, explicit reload, invalid-source suppression, control absence,
and a real 1400x900 offscreen paint. The shared-window test also proves reload
adds no VirtualSerial message or ARM.

`tests/test_replay_model.py` covers robot/fleet filtering, exact current event,
robot-only last-recorded state basis, R1/R2 cursor isolation, stable reload,
truncated-prefix UNKNOWN behavior, and fail-closed invalid sources.
`tests/test_replay_widget.py` covers manual local cursor controls, source
propagation, control absence, and a real 1400x900 offscreen paint. The shared-
window test proves Replay selection stays synchronized and adds no Serial or ARM.
